# 00. Архитектура среза «Бой на орбите» в Godot 4.7.2

Это итог проектирования. Три архитектора (A, B, C) независимо построили
пробные проекты в настоящем Godot 4.7.2 и замерили каждое своё решение;
судья перепроверил главные числа сам и выбрал, что берём. Здесь —
принятые решения по восьми вопросам: решение, почему, что проверено на
деле (с цифрами), чего избегаем. Как это строить по шагам — в `plan.md`.

Что срез делает, решено раньше и здесь не пересматривается:
- **поведение боя** — доктрина, часть 09 (а не нынешний бой из JS);
- **правила и числа, которые переходят без изменений**, и ловушки — части
  01–08 (их разделы 7 говорят, что доктрина отменяет или меняет);
- **кланы среза** — Тройден и Плэктор; данные и правила Рииза
  (скрытность) и Девиана (злой купол) описаны и загружаются, но включаются
  отдельными пакетами после среза;
- **цель** — программа для Windows и Linux, мышь и клавиатура.

«Проверено» ниже значит: сделано в Godot 4.7.2 (редактор `godot`,
выгруженные сборки, `xvfb-run` с lavapipe/llvmpipe, GitHub Actions) на
этой машине (Xeon 2,1 ГГц, 4 ядра, без видеокарты). Пробные проекты
лежали в рабочей папке сеанса (`scratchpad/godot/arch-A|B|C`) и в
репозиторий не входят. Где число — замер одного архитектора, не
перепроверенный судьёй, это сказано.

Сайт (three.js, папка `game/`) этот проект НЕ трогает.

## 1. Слои и двери между ними

```
            команды (очередь, с номером шага)
  input/ ─────────────────────────────┐
  ui/    ─────────────────────────────┤
                                      ▼
                    ┌─────────────────────────────────┐
  tools/bench ────▶ │ sim/  Battle (RefCounted)       │  шаг 1/30 с, своё зерно
  tests/ (модель) ─▶│  корабли, машины, снаряды       │
                    │  events[] шага, feed_log,       │
                    │  toast_log, cmd_log, metrics    │
                    └───────────────┬─────────────────┘
                     только чтение  │
            ┌───────────────────────┼─────────────────────────┐
            ▼                       ▼                         ▼
      view/ (Node3D)           ui/ (Control)            audio/
   интерполяция, корабли,   панель, ростер, лента,   по событиям шага
   эффекты по событиям      полоски, итоги
```

Правила (уроки частей 05 ловушки 37–40 и подсказок 5.2 частей 01–08):

1. **Модель не знает, что такое узел.** В `godot/sim/` нет `extends Node`,
   `get_tree()`, `Time.*`, `Engine.*`, `Input.*`, `randf()`/`randi()` без
   генератора боя, сигналов наружу. Это проверяет тест грепом.
2. **Вид и интерфейс в модель не пишут.** Всё, что меняет бой, — команда
   через одну дверь `battle.queue(cmd)`. Клавиша и кнопка зовут ОДНУ
   команду (часть 02, 5.2: «клавиши — прямо в команду, без поиска кнопки»).
3. **Команда применяется в начале следующего шага** и пишется в журнал.
   Бой = зерно + журнал команд: любой бой, в том числе сыгранный
   человеком, повторяется до шага — так пользователь может прислать
   «запись» ошибки.
4. **Время боя — числом шагов, а не `Engine.time_scale`.** Скорость
   1×/2×/4× — сколько шагов сделать за кадр; пауза — ноль шагов. Камера,
   миникарта, наведение и окна живут на настоящем времени и на паузе
   (часть 06, ловушка 16). Шаг никогда не растягивается.
5. **Вид забирает события после КАЖДОГО шага**, а не раз в кадр: на 4×
   за кадр бывает несколько шагов, и список событий шага очищается в его
   начале.

## 2. Модель боя (вопрос 1)

### 2.1 Решение
Модель боя — чистый GDScript (`RefCounted`, ни одного узла) в папке
`godot/sim/`, разбитой по областям правил. Постоянный шаг `STEP = 1/30` с,
свой цикл по накопителю в слое вида (раздел 3). Физический движок Godot,
`Area3D`, `_physics_process` и `Engine.time_scale` модель не трогает.

### 2.2 Почему — замерено, а не по вкусу
| вариант (60 кораблей + 120 машин, неуязвимы, редактор) | мс на шаг | кто мерил |
|---|---|---|
| данные, каждый с каждым (как в JS) | 3,36–3,63 | B |
| **данные, упакованный снимок для пар + сетка 200 для ПВО** | **1,43–1,51** (судья: 1,54) | B, перепроверено |
| то же в выгруженной сборке | 1,27–1,31 | B |
| логика в узлах (`Node3D` + `_physics_process`) | 1,59–1,72 (+8–15%) | B |
| узлы + `Area3D` для купола и целей ПВО | 2,51–2,53 (+70%) и **опоздание на один физический кадр** | B |
| построчный перенос JS (C), «Генеральное» с доктриной | **4,56**, худший шаг 24 мс, 18,6 с ЦП на бой | судья |
| модель A, «Генеральное» Плэктор × Плэктор (68 кораблей, до 192 машин), зерно 1 | **1,08** (p99 3,1, худший 8,0 на шаге 91), 7,05 с ЦП на бой | A, перепроверено |
| B, 68 + 192, до 105 ракет | 2,06 (p99 4,4) | судья |

Выводы:
- **Узлы как носитель логики почти не дороже (+8–15%)**, поэтому их
  отвергаем не за скорость, а за порядок шага (часть 03, 2.1: поля РЭБ →
  видимость → ИИ → корабли по порядку → машины → снаряды; порядок узлов
  в дереве меняется от рождения ракеты), за снимок для двух ИИ (05,
  ловушки 41–42) и за прогоны без сцены.
- **`Area3D` для логики — нет**: +70% и запаздывание на кадр, а часть 04
  (2.16) требует, чтобы поле РЭБ считалось в начале ТОГО ЖЕ шага.
- **Модели A и B равноценны по скорости** (обе на границе бюджета М15
  «шаг ≤ 2 мс» при пиковой нагрузке). 0,67–0,80 мс у A — это среднее
  за весь бой в выгруженной сборке; к концу боя нагрузка спадает.
- **Сто боёв идут без сцены**: A — 100 боёв «Сражения» за 42,4 с на
  четырёх процессах (выгруженная сборка); B — 77 с.

### 2.4 Порядок шага
Порядок частей 03 (2.1) и 05 (2.2) сохраняется; доктрина добавляет
снимок для ИИ и замеры. Урон применяется сразу (часть 03, 5.2: перенос
урона в конец шага поменял бы исход перестрелок «двое убивают друг
друга»).

```gdscript
# sim/battle.gd — порядок шага. space.js:3925 simStep · часть 05, 2.2; ДОКТРИНА 09, 4.5 и 8.1
func step() -> void:
	time += STEP
	steps += 1
	events.clear()
	Commands.apply_due(self)          # приказы, поставленные на этот шаг
	Space.rebuild(self)               # живые по сторонам + упакованный снимок, пары (2.5)
	Ecm.update(self)                  # поля помех — один раз, по положениям начала шага
	GroundGun.update(self)            # орудие планеты
	Vision.update(self)               # кто кого видит; seen_pos — ДО ИИ (05, ловушка 39)
	_arrive_reinforcements()          # прибывшие — до ИИ
	var orders: Array = []            # оба ИИ думают по ОДНОМУ состоянию начала шага
	for a in ai:
		orders.append(a.think(self) if a.due(self) else [])
	for o in orders:
		Commands.apply_ai(self, o)
	for s in ships:
		if not s.dead: _update_ship(s)     # гипер/ион → цели → движение → оружие → ПВО
	for c in crafts:
		if not c.dead: Air.update_craft(self, c)
	for p in projs:
		if not p.dead: Weapons.update_proj(self, p)
	_hangars_and_cleanup()            # места ангаров, уборка, звенья
	_check_teeth()                    # «нечем бить» — ДО конца боя
	_check_end()
	metrics.sample(self)
```

- Внутри `_update_ship` — порядок части 03 (2.1): копит гипер — только
  накачка; ион; флагман ниже `flee` — в гипер; цели; движение (у тяжёлых —
  `HeavyDoctrine.capital_want`, раздел 2.7); оружие — ПОСЛЕ движения
  этого шага; ПВО.
- **Тики двух ИИ разнесены по шагам** (у каждого свой счётчик), чтобы
  тяжёлые тики не складывались в один худший шаг; но если они совпали,
  оба думают по одному снимку (09, 4.5). Что сам СДВИГ фазы не даёт
  перевеса одной стороне (её ИИ всегда отвечает первым) — не проверено:
  это ловит зеркальный бой М13, и тогда фаза берётся от зерна боя,
  а не от стороны.
- **Пуски звеньев разносятся по шагам**: худший шаг A (8,0 мс на
  шаге 91) — это первый тик ИИ, когда все носители поднимают все звенья
  разом.
- В тике — без лямбд, `filter`, `map` и словарей с переменными ключами:
  у C всплески худшего шага шли ровно от них.

### 2.5 Хранение: объекты для логики, упакованный снимок для пар
GDScript медленно читает поля ЧУЖОГО объекта (два поиска по имени).
Замер A — расталкивание на 41 корабле, 300 повторов, результаты
совпали до бита:

| способ | мкс на проход |
|---|---|
| объекты, каждый с каждым (как в JS) | 828 |
| объекты, сетка 180 | 300 |
| **упакованные массивы, пары `i < j`** | **82** |

Поэтому в начале шага `Space.rebuild` один раз собирает снимок живых
кораблей в `PackedVector3Array`/`PackedFloat32Array`/`PackedInt32Array`
и одним проходом пар считает всё парное: толчки расталкивания, ближайшего
чужого, ближайшего чужого корабля к тяжёлому (для «вплотную»). ПВО и
машины ищут цели по упакованным положениям чужих машин и снарядов.

```gdscript
# sim/space.gd — пары по снимку начала шага. space.js:1309 · часть 02, 2.10
# ОТЛИЧИЕ: в JS каждый корабль видел уже сдвинутых соседей; здесь — положения
# начала шага. Разница — доля шага (≈2 ед. при 60 ед/с); М9 и наложения перемеряются.
for i in n:
	var pi := pos[i]; var hi := hull[i]; var si := side[i]
	for j in range(i + 1, n):
		var off := pi - pos[j]
		var d2 := off.x * off.x + off.z * off.z        # бой плоский (09, 11.6)
		var foe := side[j] != si
		if foe:
			if d2 < near_d2[i]: near_d2[i] = d2; near[i] = j
			if d2 < near_d2[j]: near_d2[j] = d2; near[j] = i
		var mn := (hull[j] + hi) * (1.15 if foe else 1.0)
		if d2 < mn * mn and d2 > 0.0001:
			var dd := sqrt(d2)
			var k := (mn - dd) / mn / dd * (1.1 if foe else 0.8)
			push[i] += off * (k * vmax[i])
			push[j] -= off * (k * vmax[j])
```

**Сетка 200×200** (как у B: 3,4 → 1,5 мс вместе с проходом пар) — только
когда профиль по частям покажет, что поиск целей ПВО и авиации стал
главной статьёй шага. При 68 кораблях пар 2278, и проход пар дешевле
обслуживания сетки; для сотен машин и ракет — наоборот.

### 2.6 Оружие по роли, а не `guns[0]`
```gdscript
class WeaponDef:
	var role: StringName     # &"main" &"sec" &"light" &"missile" &"pd"
	var key: StringName      # строка таблицы урона: &"heavy" &"sec" &"light" &"missile" &"pd"
	var dmg: float
	var cd: float
	var rng: float
	var dead: float          # мёртвая зона; 0 — нет
	var charge: float        # накачка главного калибра (флагман 1,8 с); 0 — нет
	var salvo: int           # ракетный пакет «Синхо»: 3 ракеты, разброс spread
	var spread: float
	var mounts: int          # установки, у каждой свой таймер
class ShipDef:
	var main: WeaponDef      # ссылки по роли: круг, поводок, «главный в группе» берут отсюда
	var sec: WeaponDef
	var light: WeaponDef
	var missile: WeaponDef
	var pd: WeaponDef
```
Батарея (`sec`) заводится загрузчиком из `doctrine.json` с формулой клана.
Ключ урона у неё свой — замер М7 делит урон по ключу без остатка.
Несколько орудий одной роли в выгрузке (два `heavy` у флагмана) загрузчик
сводит в одно определение с `mounts = 2`, **только если они одинаковы
во всех полях**; разные — громкий отказ при загрузке, а не молча взятое
первое (то же `guns[0]`, только в загрузчике). Сейчас (проверено по
`space_data.json`) у всех кланов они одинаковы.

**«Где главный калибр не может выстрелить, подход обязан это знать»**
(часть 03, ловушка 5; 09, 2.10) — одна функция на все места:
```gdscript
# ДОКТРИНА 09, 1.2 и 2.1
func main_reach(s: Ship, d: float) -> int:   # -1 ближе мёртвой зоны, 0 в поясе, 1 дальше
	var w := s.def.main
	return -1 if d < w.dead else (1 if d > w.rng else 0)
```
Её зовут выстрел (проверка ДО накачки), выбор цели, подход и отход,
строка «чем занят» и замер М1. Разъехаться им нечему.

### 2.7 Тяжёлые: состояние пояса — явным значением
`enum Belt { HOLD, APPROACH, IN_BELT, RETREAT, PINNED, FUTILE }` у каждого
тяжёлого; переход — в одной функции `capital_want()` по таблице 09, 2.9.
Состояние — поле, а не вывод из пяти условий: по нему строит строку «чем
занят» интерфейс, по нему считает М6 стенд, по нему читается журнал
одного боя (порядок поиска ошибки 09, 8.4). Смена состояния пишется
в журнал боя.

### 2.8 Задел на повреждения по узлам (09, раздел 10)
- Всё, что зависит от узла, — функцией, а не полем: `thrust()`, `turn()`,
  `max_speed()`, `armor_toward(dir)`, `weapon_ready(role, i)`,
  `pd_barrels()`, `ecm_power_cap()`, `hangar_bays()`, `hp_frac()`,
  `can_hurt()`, `threat()`. В срезе каждая отдаёт число из определения.
- **Тормозной путь `arrive_speed` берёт ту же `thrust()`, что разгон**
  (часть 02, ловушка 2). Тест «двигатели × 0,5: разгон и торможение
  меняются вместе, перелёта нет» стоит в срезе с первого пакета полёта.
- Урон — одна дверь с направлением: `damage(target, amount, key, source,
  from_dir)`. Бронь — `armor_toward(from_dir)`, пока одно число. Учёт
  М7 — внутри неё же.
- Ион, ЭМИ, ослепление — «выключатели узла со сроком» одного вида
  (`off_until[node]`), а не флажки по месту: выбитый узел потом — тот же
  выключатель без срока.
- Узлы перечислены в данных корабля (`doctrine.json → nodes`), а в сцене
  корабля — узлами с теми же именами (`turret_i/muzzle_i`, `engine_*`,
  `pd_*`, `aux_*`, `emitter`, `bay`). Выбор мышью разбирается в одном месте
  и сможет отдавать пару «корабль, узел».
- **Картинка не должна закрыть узлы тоже.** Две вещи, которые выглядят
  как «оптимизация», закрыли бы их молча: (1) выгрузка модели, сливающая
  ВЕСЬ корабль по материалу в ~9 мешей (проба 08, П.3) — башню потом не
  повернуть и не «выбить»; поэтому сливаем по материалу ВНУТРИ узла
  (08, 7.2 п. 8; 5.2); (2) перевод корпусов в `MultiMesh` ради кадров —
  допустим только с точками узлов как ДАННЫМИ модели (смещения
  `turret_i`, `engine_*`, `aux_*`), а не как узлами сцены, которые
  пропадут вместе с корпусом.

### 2.9 Команды и повтор боя
```gdscript
# input/ и ui/ — только так
battle.queue({"op": &"focus", "ids": sel_uids, "target": t.uid})
# sim/commands.gd
func queue(c: Dictionary) -> void:
	c["step"] = battle.steps + 1      # применится в начале следующего шага
	pending.append(c)
	cmd_log.append(c)                 # повтор = зерно + cmd_log; сохраняется в user://
```
Ссылки в командах — по `uid`, не по объекту: журнал переживает файл.
Режим `-- --replay файл` проигрывает бой из журнала. **У записи —
заголовок**: версия сборки, отпечаток данных (`space_data.json`
и `doctrine.json`) и зерно. Запись верна только для той сборки и тех
чисел, на которых сыграна: проигранная другой сборкой, она молча дала
бы другой бой, и «присланная ошибка» не повторилась бы. Чужая сборка —
отказ словами, а не проигрыш. Повторяемость Windows ↔ Linux — 2.11.

### 2.10 События и журналы
- `events` — список событий ЭТОГО шага (`[&"beam", кто, в кого, роль]`,
  `[&"destroyed", кто, кем]`, …). Вид забирает его после каждого шага для
  эффектов и звука; метрики — внутри шага. **Сигналов из шага нет**: если
  виду удобен сигнал «корабль погиб», его отдаёт узел-проигрыватель ПОСЛЕ
  шага, по списку событий (решение судьи: сигнал посреди шага даёт виду
  вызвать что-то, пока бой не досчитан).
- `feed_log`, `toast_log` — долгие журналы в состоянии боя, с игровым
  временем (как в JS, часть 05 ловушка 38, часть 07 ловушка 42): лента
  и полоски их только показывают, тесты читают их, а не экран.

### 2.11 Случайность и повторяемость
- **Два генератора с первого дня** (находка C): `rng` — только бой (зерно
  на бой), `fx_rng` — только картинка. В JS вспышки в `destroy` брали
  `Math.random` — перенесёшь как есть, и исход боя зависит от того,
  рисуется ли он.
- Обход только массивов и словарей с порядком вставки; никакого
  настоящего времени в модели; бой плоский — у всех `y = 0` в логике,
  высота — только у вида (09, 11.6).
- **Проверено** (A, судья повторил первое): отпечаток состояния после
  полного боя одинаков в двух запусках выгруженной сборки и в редакторе
  (`375834857`, 68 кораблей, 218 с боя); на этой машине и на машине
  GitHub Actions (`2883674998`, `4104239335`); в Linux и в WebAssembly
  (`3284205486`). B: хэш совпал между процессами и между редакторским
  и выпускным бинарником. **Windows не проверен** — сверка отпечатка
  Linux ↔ Windows ставится в CI (раздел 9).

### 2.12 Память
`RefCounted` не собирает кольца ссылок (звено ↔ машина, бой ↔ ИИ, цели).
Замер A: без разрыва колец +250 объектов на бой; после `dispose()` —
ровно 1562 объекта после каждого боя из пяти (судья повторил). У B стенд
при выходе терял 85 объектов, у C — 108 за два боя: `dispose()` не звали.
Правило: `battle.dispose()` после каждого боя; тест «объектов после N
боёв не больше, чем после первого».

### 2.13 Бюджет времени
Цель М15: шаг без отрисовки ≤ 2 мс на «Генеральном». **Мерить на
худшем бое, который может собрать игрок**: «Генеральное» Плэктор ×
Плэктор с вызванным резервом — 83 корабля и до 240 машин (68 в пробах —
тот же бой без резерва, а резерв игроку в «Генеральном» доступен; пар
кораблей 3403 против 2278, в полтора раза больше). Проба A проще
полной доктрины (нет подкреплений, полного ИИ, РЭБ-правил 09, 1.7) —
закладываем рост ×1,5–2 и держим в каждом отчёте стенда p50, p99,
худший шаг и его номер. Порядок мер, если не влезаем: профиль по частям
→ упакованный снимок для всего парного → сетка для ПВО и авиации →
разнести пуски и тики ИИ → и только с замером — горячие циклы в
GDExtension (это сборка C++, которой в проекте нет). Потоки внутри
одного боя — нет: повторяемость дороже.

### 2.14 Доктрина сразу, а не построчный перенос старого боя
Спор C против A и B решён в пользу доктрины: пользователь прямо решил,
что в Godot переносится не нынешний бой, а доктрина. При «сначала
старый бой, потом доктрина флажком» срез откладывается на пакет,
`update_ship` и тик ИИ живут с двумя путями, и каждая правка делается
дважды (C сам называет это долгом).

**Что берём у C:**
- Что переходит БЕЗ изменений — полёт (часть 02), таблица урона и бронь
  (03), механика ПВО, ракет, авиации и РЭБ там, где 09 её не трогает
  (04), — переносится построчно и сверяется с эталонами JS юнит-тестами
  модели. C показал, что это достижимо: таблица 2.22 части 02 повторена
  с расхождением не больше 0,003 с (21 время прихода и 7 торможений).
- Над каждой перенесённой функцией — пометка
  `# space.js:NNNN имяJS · часть NN, раздел`; отличие — только помеченное:
  `# ОТЛИЧИЕ: … (почему)` или `# ДОКТРИНА 09, §…`. Непомеченное отличие —
  ошибка переноса.
- `tools/map_names.py` (по желанию) — список «перенесено / не переносится
  с причиной» только для переносимых функций.

**Старого поведения ровно столько, сколько требуют флажки отката 09, 8.4**:
старый подход 0,68 R, старый ИИ, старое ПВО, старые помехи, старая
камера, подход без доли сближения, подход без торможения у чужих, «путь
чист 0,55 R», заход бомбардировщиков прямо на цель, патруль над
серединой, РЭБ на 0,1 L со второй лёгкой шеренгой. Задача каждого
флажка — провалить свой замер, а не повторить JS до секунды. Полного
старого боя и сверки ИИ с таблицей 05, 2.18 в срезе нет.

### 2.15 Чего избегаем в модели
- логики в узлах, сигналов посреди шага, `Area3D` для правил;
- словарей вместо классов: опечатка в словаре молча заводит новый ключ
  (проверено C: `e.hpp = 5`), и словарь медленнее в 1,46 раза
  (1,65 против 1,13 мс на шаг расталкивания);
- `guns[0]` и «первого орудия» где угодно (09, 9.5 п. 1);
- растянутого шага: на 4× делаем больше шагов, а не длиннее;
- `.catch`-подобного «не пришло — ну и ладно» при сборке состояния из

## 3. Плавность: модель 30 Гц на экране 60+

Сглаживать обязательно: C замерил сдвиг корабля между кадрами 7, 0, 7, 0
точек на экране 60 кадров без сглаживания и 3,1–4,0 точки каждый кадр
со сглаживанием.

**Решение — своя интерполяция в слое вида.** Встроенную
`physics_interpolation` и шаг боя в `_physics_process` (B, C) не берём:
она привязана к физическому такту движка, каждый переиспользованный слот
пула `MultiMesh`, каждый выход из гипера и каждое рождение требуют
`reset_physics_interpolation`, иначе тянется хвост от прежнего места;
камеру пришлось бы исключать. Своя смешивалка — двадцать строк, одинаково
работает без окна и снимается тестом. Телепорт — флажок сущности в
модели (`jumped_at_step`), на нём смешивание не идёт.

```gdscript
# view/battle_view.gd
const MAX_STEPS := 8          # 4× при 30 кадрах — 4 шага; больше — бой замедляется, а не дробит шаг
func _process(delta: float) -> void:
	if not paused and not battle.over:
		acc += minf(delta, 0.1) * speed
		var n := 0
		while acc >= Battle.STEP and n < MAX_STEPS:
			_remember_prev()                 # прошлое положение каждой сущности
			battle.step()
			_consume_events(battle.events)   # эффекты и звук ЭТОГО шага
			acc -= Battle.STEP
			n += 1
		if n == MAX_STEPS: acc = 0.0         # не копим долг: лучше медленнее, чем рывками
	_draw_state(acc / Battle.STEP)           # lerp положения, lerp_angle курса
```

- ОТЛИЧИЕ от JS: там на 4× шаг доходил до 0,2 с (часть 02, вопрос 19;
  часть 05, 2.1). Здесь шаг всегда 1/30, на медленной машине бой идёт
  медленнее настоящего времени, но не меняет правил.
- Проверка: тест плавности через Movie Maker (`--write-movie`,
  `--fixed-fps 60`) — сдвиг корабля между соседними кадрами ровный.
- Запасной путь (от B): встроенная интерполяция (`set_buffer_interpolated`
  у `MultiMesh` в 4.7.2 есть, проверено судьёй; по умолчанию выключена),
  если своя где-то не справится.

## 4. Выбор мышью

**Решение — своя функция без физического движка, в порядке части 06,
2.4.4:**
1. **Луч по корпусу**: пересечение луча камеры (`project_ray_origin`,
   `project_ray_normal`) с капсулой корпуса, посчитанной по данным
   модели (длина и ширина из выгрузки модели) и ИНТЕРПОЛИРОВАННОМУ
   положению и курсу. Ближайшее попадание вдоль луча.
2. **Подпись** (`labelHits`): прямоугольник подписи, от подписи до самого
   корабля (часть 07, ловушка 23).
3. **Ближайший в 30 точках** — по проекции центров.
4. Машина отдаёт своё звено.

Скрытые и мёртвые отсекаются одним фильтром видимости — тем же, что у
подписей, миникарты и купола (C18). Эффекты в кандидаты не входят по
устройству (C29): их нет в списке, который перебирает функция.

Почему не физический луч (B, C): спецификация требует «луч по моделям»,
и `wardAt` (охрана своего) берёт ТОЛЬКО прямое попадание в корпус;
капсула по данным это даёт. Физические тела — второе состояние, которое
надо держать в согласии с моделью и физическим тактом; машины всё равно
рисуются `MultiMesh`, и физический луч их не видит. Своя функция
проверяется без окна и без физического кадра.

Запасной путь (проверен B и C): `Area3D`/`StaticBody3D` с капсулой
и `intersect_ray` — 1–2,5 мкс на луч, свечение без коллизии не мешает,
у скрытого `collision_layer = 0`. Брать, если своя капсула окажется
сложнее.

## 5. Сцена и отрисовка (вопрос 3)

### 5.1 Отрисовщик
- **Forward+** (Vulkan на Windows и Linux), откаты `fallback_to_d3d12`
  и `fallback_to_opengl3` включены — так по умолчанию в 4.7.2 (проверено).
  **MSAA 3D 4× включить явно** (по умолчанию 0). Свечение — после него
  (часть 08, ловушка 1 закрывается устройством).
- Откат на **Compatibility** на старой видеокарте меняет картинку:
  свечение от одного и того же шейдера 0,62 → 0,37 (A); один и тот же
  кадр различается в среднем на 57 из 255 (PSNR 11,3, B). И главное —
  **ручной выпуск частиц (`emit_particle`) в Compatibility не работает
  вовсе**: движок пишет «The Compatibility renderer does not support
  manually emitting particles» (проверено судьёй). Отсюда правило: ни
  один эффект, который ГОВОРИТ игроку о бое (выстрел, попадание, гибель),
  не строится на `emit_particle`.
- При запуске игра пишет в журнал, какой отрисовщик поднялся; счётчик
  кадров (F3) показывает это на экране. Проверены только НАСТРОЙКИ
  (в 4.7.2 по умолчанию `driver.windows = vulkan`, откаты включены —
  перепроверено при проверке плана); что поднимется на компьютере
  пользователя, не проверено ничем: Windows-сборка в облаке шла без
  окна, а здесь видеокарты нет. Это первое, что сообщает итог замера
  кадров (G0).

### 5.2 Корабли
- **Тяжёлые и лёгкие — сцена-узел на корабль** (`view/ship_visual.tscn`):
  `hull`, `turret_i/muzzle_i`, `engine_*`, `pd_*`, `aux_*` (установки
  батареи), `emitter` (РЭБ), `bay` (ангар) — те же имена, что узлы
  в данных (09, 10.5). Кораблей до 83 («Генеральное» Плэктор × Плэктор
  с резервом игрока); вызовов отрисовки у всех трёх проб 107–318 (A: 58,6
  узлами против 15 у `MultiMesh` по классам; C: 178 в Forward+, 318
  в Compatibility). Что это норма для его видеокарты — **предположение,
  а не замер**: видеокарты здесь нет, и вызовов станет больше от слияния
  по узлам (ниже) и от резерва. Проверяется только итогом замера кадров
  у пользователя (G0, G9). Обновление вида на процессоре 0,2–0,53 мс
  на кадр (68 кораблей, до 182 машин, 68 подписей; на 83 — перемерить).
- Модели — выгруженные процедурные корабли three.js «под Godot» (часть
  08, приложение П.3): панели развёрнуты, меши слиты по материалу, нормали
  плоские, эффекты сняты, точки пустыми узлами, картинки JPEG. **Слиты
  по материалу ВНУТРИ узла** (корпус, `turret_i`, блок двигателей, `aux_*`
  и т. д.), а не по всему кораблю, как в пробе П.3 (~9 поверхностей
  вместо 18–52 мешей): иначе узлов в модели нет и повреждения по узлам
  закрыты на стороне картинки (08, 7.2 п. 8; 2.8). Цена — больше
  вызовов отрисовки; замер в G0. Проба: флагман Тройдена 682 КБ, 6000
  треугольников, длина рамки 206,91 = `len`. Делает это
  `godot/tools/export_ships.mjs` (Playwright + страница с `buildShip`).
  Уровни детализации у кораблей — выключить или проверить глазом
  (у слитых плит 2520 → 1176 → 168 — вдали обшивка пропадёт).
- **Длина модели меряется по `AABB`** без эффектов и сверяется с
  `model_len` выгрузки (±20%, C88); у приезжей `.glb` — тем же правилом.
- Не удержим М15 на машине пользователя — корпуса дальнего плана
  переводятся в `MultiMesh` на модель; это правка только `view/`,
  и точки узлов при этом остаются данными модели (2.8).

### 5.3 Авиация, снаряды, эффекты
- **Авиация, снаряды, трассы, вспышки — `MultiMesh`** (их сотни; 200
  машин — один вызов отрисовки).
- **Эффекты по событиям боя — пул `MultiMesh` с анимацией в шейдере**:
  место и время рождения в данных экземпляра (`INSTANCE_CUSTOM`), рост
  и угасание считает вершинный шейдер от `now`. Новое событие пишет один
  экземпляр, кольцо отдаёт самый старый слот (часть 08, ловушка 5, C44);
  слот при выдаче заполняется ЦЕЛИКОМ (часть 08, ловушки 19–20: «ring()
  сбрасывает flat», «спрайт сбрасывает smokeEvery»). Проверено A в обоих
  отрисовщиках: 1 вызов отрисовки, 0,03–0,17 мс ЦП на 15 вспышек за кадр.
- `GPUParticles3D` — только `emitting`/`restart` (не `emit_particle`) для
  непрерывного: факелы, дым горящего корабля, крупные взрывы. В
  проверочной сборке у всех частиц `use_fixed_seed` и постоянное зерно:
  иначе два прогона расходятся в 181–2814 точках на кадр, с зерном —
  14 кадров из 14 совпали до точки (C).
- Лучи и трассы — квады с шейдером, разворачивающим квад вокруг оси луча
  к камере (часть 08, 5.2), с нижним пределом толщины в точках экрана
  (09, 11.8): при 2400 трасса ПВО иначе меньше точки.
- Сроки эффектов — на часах модели (момент события), а не наоборот
  (часть 08, ловушки 16–17).

### 5.4 Подписи

## 6. Интерфейс (вопрос 4)

### 6.1 Слои
`CanvasLayer` по порядку: подписи (5) → HUD (10) → подсказки и полоски
(20) → окна (60 меню паузы / 70 справка / 80 вопрос). Цвета, кегли,
отступы — одна `ui/theme.tres`; состояние подписи и кнопки задаётся кодом
в ОДНОМ методе «применить вид», а не наслоением стилей (07, 5.2).

при `canvas_items` с базой 1920 всё на 1366 ужималось в 0,71, кегль 15
становился 10,7 (B). Раскладка 07, 2.2 дана в точках на 1920×1080
и 1366×768; сканер гоняется на обоих.

### 6.2 Мышь: строитель ставит фильтры (проверено на 4.7.2)
| узел | `mouse_filter` по умолчанию | что делать |
|---|---|---|
| `Control`, `Panel`, `PanelContainer`, `ColorRect` | `STOP` | всем, кто только раскладывает, — `IGNORE` (иначе пустая полоса глотает щелчок, C135 — проверено) |
| `HBoxContainer` и другие контейнеры | `PASS` | явно ставить `IGNORE` |
| `Label` | `IGNORE` | — |
| `Button` | `STOP` | ловят только кнопки и ячейки ростера |
| подложка окна | `STOP` целиком | щелчок по тексту окна не закрывает его (06, ловушка 34) |

Строитель интерфейса (`ui/builder.gd`) проходит дерево и ставит `IGNORE`

HUD (тема этого не умеет). Прозрачный родитель НЕ делает прозрачными
детей (C2 закрыт устройством Godot — проверено).

### 6.3 Кнопки не пересоздавать (C30)
Проверено: кнопку убрали и поставили новую на то же место между нажатием
и отпусканием — щелчка не получил никто. Панель пересобирается только
при смене ключа «состав выделения + набор команд»; текст, `disabled`

### 6.4 Фокус и клавиши
- У `Button` по умолчанию `FOCUS_ALL`: щёлкнул мышью — Пробел жмёт её ещё
  раз (проверено). У кнопок HUD — `FOCUS_NONE`; Пробел паузы — своё

- Действия Input Map — по `physical_keycode` (проверено: «р» на месте H
  ловится, по `keycode` — нет). `is_action_pressed` повтор пропускает по
  умолчанию; разбор сырого `InputEventKey` обязан смотреть `echo`.
- Клавиша и кнопка зовут одну команду `battle.queue(…)`.

### 6.5 Жест, начатый на поле
Проверено (A и C): ПКМ нажали над полем, повели над панелью `STOP`,
отпустили там — отпускание в `_unhandled_input` пришло, а движение над
панелью — нет (0 из 7 событий): поворот камеры замирал бы. Жест, начатый
на поле, дослушивается в `_input` (там приходит всё), флажок жеста —
в слое ввода. Это поправка к части 06, 5.2.

### 6.6 Окна и подсказка — свои
- `ui/modal.gd`: подложка `STOP` на весь экран + панель. Правила «окно
  глотает все клавиши, кроме F3/F11», «вопрос ставит паузу и возвращает
  скорость», «закрыть по фону — только если и нажали на фоне», «Esc —
  верхнему» проще держать в одном своём классе, чем обходить поведение
  `Window` (это отдельный вьюпорт со своим разбором ввода).
- Поведение штатного `ConfirmationDialog` — эталон для теста своего окна
  (проверено): повтор Esc окно не закрывает; первый Esc закрывает и до
  меню под ним не доходит; следующий повтор приходит в поле с `echo`.
- `ui/tooltip.gd`: своя подсказка сразу и в пределах экрана; штатная ждёт
  0,5 с (`gui/timers/tooltip_delay_sec`, проверено) и за край не следит.
- У узлов интерфейса — `process_mode = ALWAYS`: лента гаснет по игровому
  времени с нижней границей 3 настоящих секунды, полоски — по настоящему
  времени и на паузе (07, 5.2).
- Числа в тексты — только форматом (`"%d" % x`, `"%.1f" % x`), а не
  `str()`: `str(12636.0)` даёт «12636.0», и панель написала бы
  «прочность 12636.0/12636.0». Формата `%g` в GDScript нет (ошибка
  разбора).

  округлён (16.099999999999998 — настоящее число игры; 01, ловушка 3).

- **`.tres` для чисел боя нет**: это вторая правда о тех же числах. Ресурсы

## 8. Автотесты и прогоны баланса (вопрос 2)

### 8.1 Три яруса, свой прогонщик

Свой маленький прогонщик (`tests/run.gd`, `extends SceneTree`): находит
`tests/test_*.gd`, зовёт функции `test_*` (они могут `await`), печатает
итог и последней строкой `RESULT checks=N fails=M`. Дополнений (GUT,
GdUnit) нет: сборки нет, а нужен он на сотню строк.

### 8.2 Обёртка запуска — каждое правило проверено
`godot/tools/run_tests.sh` (локально и в CI):
1. **`godot --headless --path godot --import` первым**: без импорта
   `class_name` не находится («Could not find type», B).
2. **`--check-only` по всем скриптам**: код 1 на ошибке разбора, 0 на
   целом (судья).
3. **Каждый прогон — под `timeout`**: сцена со сломанным скриптом висит
   вечно (выход по `timeout`, код 124); ошибка во время работы `-s`-скрипта
   тоже вешает — до `quit()` дело не доходит.
4. **От прогона требуется строка `RESULT`**; её нет — провал.
5. **Любой `SCRIPT ERROR` в выводе — провал**: в редакторе ошибки времени
   выполнения дают код выхода 0, и скрипт, подгруженный через `load()`
   и сломанный, тоже даёт 0.
6. **Диагностика — в stderr (`printerr`) или в файл**: при обрыве по
   `timeout` буфер stdout теряется.
7. **Обе выгруженные сборки ЗАПУСКАТЬ** в CI — и с `-- --selftest`, и
   с окном (`--quit-after 60`): вызов РОДНОГО метода у `null` в выпускной
   сборке — `Segmentation fault` (код 139), а в редакторе — та же строка
   даёт только `SCRIPT ERROR` и код 0. СКРИПТОВЫЙ метод у `null` и чтение
   поля у `null` в выпускной сборке молча ничего не делают — ошибка вовсе
   пропадает из виду (G0a).
8. Процессы останавливать только по PID, не `pkill -f` по имени (B оборвал
   так чужой прогон).

### 8.3 Ввод — настоящими событиями, «кто под точкой»
```gdscript
# tests/hooks.gd
func click(pos: Vector2, button := MOUSE_BUTTON_LEFT) -> void:
	var mv := InputEventMouseMotion.new(); mv.position = pos; mv.global_position = pos
	Input.parse_input_event(mv)
	var ev := InputEventMouseButton.new()
	ev.button_index = button; ev.pressed = true; ev.position = pos; ev.global_position = pos
	ev.button_mask = MOUSE_BUTTON_MASK_LEFT if button == MOUSE_BUTTON_LEFT else MOUSE_BUTTON_MASK_RIGHT
	Input.parse_input_event(ev)
	await process_frame                 # события разбираются в следующем кадре
	var up := ev.duplicate(); up.pressed = false; up.button_mask = 0
	Input.parse_input_event(up)
	await process_frame; await process_frame

func hovered_at(pos: Vector2) -> Control:   # аналог elementFromPoint
	var mv := InputEventMouseMotion.new(); mv.position = pos; mv.global_position = pos
	Input.parse_input_event(mv)
	await process_frame
	return get_root().gui_get_hovered_control()
```
- **Без окна (`--headless`) это работает** — перепроверено судьёй:
  `parse_input_event`, `parse + flush_buffered_events` и `push_input`
  нажимают кнопку (6 из 6 вариантов), и с кадром между нажатием
  и отпусканием, и в одном кадре; `gui_get_hovered_control()` в центре
  кнопки отдаёт саму кнопку. Тест интерфейса B с подачей через `Input`
  без окна проходит 21 из 21 (утверждение B «22 из 23 кнопок не нажались»
  не подтвердилось). Ввод через `Input` ближе к настоящему, чем
  `push_input`: он проходит Input Map, `echo` и действия по
  `physical_keycode`.
- **Размер окна — после первого кадра**: в `_initialize` `root.size` равен
  100×100, присвоенный там размер после первого кадра откатывается
  к 64×64; `--resolution` не помогает. Задавать после `await process_frame`.
  В тестах прогонщика ловушку не воспроизвести (кадры уже прошли), поэтому
  её сторожит канарейка отдельным процессом (`tests/probe_window.gd`, G0a).
- `Input.use_accumulated_input = true` по умолчанию: несколько движений
  мыши в одном кадре сливаются — для протяжки слать по движению на кадр.
- Сканер (07, ловушка 10): каждая видимая кнопка нажимается настоящим
  щелчком в центр; под точкой — ИМЕННО она, и её счётчик в журнале
  интерфейса вырос на один. Плюс «кнопка целиком на экране»
  (`get_visible_rect().encloses(rect)`, B: Godot находит кнопку и за краем
  окна). Обратный сканер для C135: сетка точек над пустыми полосами —
  щелчок дошёл до поля.
- Клавиши — `InputEventKey` с `physical_keycode`; русская раскладка —
  `keycode = 1088` («р») при `physical_keycode = KEY_H`.

### 8.4 Доступ к состоянию вместо `window.__sp`
Тест живёт внутри Godot, мост не нужен: у главной сцены есть `battle`,
`camera_rig`, `hud`. В `tests/hooks.gd` — вопросы «где корабль на экране»
(`unproject_position`), «что под точкой экрана на столе», «кого выберет
щелчок» (та же функция выбора, что у игры), «поставить корабль»
(ставит и участок `anchor` — часть 02, ловушка 29), «убить корабль»,
«собрать бой заданного состава» (аналог `__spaceTest`).

### 8.5 Снимки
- Без окна снимков нет: у `--headless` отрисовщик-заглушка. Под
  `xvfb-run` — есть в обоих отрисовщиках (Vulkan/lavapipe и
  OpenGL/llvmpipe).
- `--fixed-fps 30` делает снимок повторяемым: два запуска, 150 кадров
  боя на 4× — 0 различающихся точек из 1280×720 (A). Movie Maker
  (`--write-movie out/f.png --fixed-fps 30`) — для покадровых проверок
  (плавность, частицы) с постоянным зерном частиц (C).
- **Эталоны снимков — свои на каждый отрисовщик** (средняя разница
  одного кадра 57 из 255) и только с этой машины и драйверов; на
  видеокарте пользователя они не совпадут — это проверка регрессий.
  Основа — **проверки-замеры по точкам**: пурпур в диске планеты, доли
  кадра, цвет по каналам, рамки кораблей (07, 4.2 п. 5; 09, 11.7).
  Сравнение — `Image.compute_image_metrics`.

### 8.6 Стенд «ИИ против ИИ»
- Ядро стенда — `tools/bench_core.gd`, две двери: в редакторе
  `godot --headless --path godot -s res://tools/bench.gd -- …`; в
  выгруженной сборке **`-s` нет вовсе** (собрана с `disable_path_overrides`),
  поэтому главная сцена читает `OS.get_cmdline_user_args()`:
  `capella.x86_64 --headless -- --bench --load battle --n 25 --seed 1000`.
- **Сто боёв — процессами, по 25 на процесс**, а не потоками: процессы не
  делят память, падение одного не трогает остальные, зерно у каждого своё.
- Ключи: `--swap` (кланы меняются сторонами — 05, ловушка 41),
  `--set путь=число`, `--overrides=файл`, флажки отката 09, 8.4
  (`--legacy-approach`, `--old-ai`, `--old-pd`, `--old-ecm`,
  `--no-share-close`, `--no-foe-brake`, `--clear-055`, `--bomber-direct`,
  `--patrol-mid`, `--ecm-01L`). «Старая камера» (`--old-camera`) —
  ключ тестов КАРТИНКИ (М14, пакет G8), а не стенда: стенд без
  отрисовки камеру не меряет. У `--old-ecm` в срезе своя оговорка:
  09, 8.4 ждёт провала М12 через купол Девиана, которого в срезе нет
  (план, G5).
- Составы (09, 8.1): «Стычка» и «Сражение» без резерва и без орудия
  планеты (баланс кланов), отдельно — быстрый бой как есть; «Офицер»
  у обеих сторон; **по 100 боёв на каждое сочетание и роль** (атакующий /
  защитник). Проба A на 24 зеркальных боях дала 15:9 — это шум, а не
  вывод.
- Отчёт — строка JSON на бой: исход, длина, фазы, М1–М13, доли урона по
  ключам, время шага (p50/p99/худший и его номер), отпечаток, ОС, сборка,
  правки. Сводку строит `tools/summarize.py`: медианы, 10% худших,
  сравнение с порогами 09, 8.2.
- На каждый пуш — дымовые 3–4 боя. Сотни боёв гоняются **в сеансе**,
  на этой машине: 100 «Сражений» — 42 с на четырёх процессах (2.2), все
  сочетания и роли — минуты. В CI — по пушу с пометкой; «по кнопке»
  (`workflow_dispatch`) — только если файл workflow окажется в ветке
  по умолчанию (9.2), на это не рассчитываем.
- **Тот же отчёт пишет и бой человека** (план, G5): строка JSON после
  итога, выжимка на карточке итога и в буфер обмена. Иначе М11 и М1–М10
  мерились бы только у «ИИ против ИИ», а свалку пользователь увидел
  в своей игре.

### 9.1 Что проверено
| что | число |
|---|---|
| выгрузка здесь | Linux 73,5–73,7 МБ (один файл, pck внутри), Windows 109,4 МБ; 4–10 с на выгрузку |
| архивы | Linux zip 27–28 МБ (tar.xz 19,2 МБ), Windows zip 36–38 МБ (у C с данными 45 МБ) — больше предела файла git 100 МБ без архива, поэтому сборки в git не кладём |

| черновик выпуска из CI | создан C (`gh release create --draft` с `permissions: contents: write`) и удалён тем же шагом |

### 9.2 Решение
Файл `.github/workflows/capella-godot.yml` в КОРНЕ репозитория (иначе
GitHub его не видит):

```yaml
on:
  push:
    branches: ['claude/capella-godot', 'claude/capella-godot-*']
    tags: ['capella-v*']                 # метки — в on.push.tags, одним ключом push
    paths: ['godot/**', '.github/workflows/capella-godot.yml']
  workflow_dispatch:
    inputs:
      battles: { description: 'сколько боёв на сочетание (0 — без стенда)', default: '0' }
      release: { description: 'выпустить как capella-vX.Y (пусто — нет)', default: '' }
jobs:
  test-build:   # ubuntu-latest
    # кэш Godot 4.7.2 и шаблонов (сверка SHA512) → --import → --check-only всех
    # скриптов → тесты модели и интерфейса → картинка под xvfb в обоих отрисовщиках →
    # дымовые бои → export_data.mjs --check и doctrine.mjs --check → выгрузка Linux
    # и Windows → ЗАПУСК Linux-сборки (--headless -- --selftest и дымовой бой,
    # отпечаток в вывод) → артефакты (7 дней)
  windows-run:  # windows-latest, после test-build
    # capella.console.exe --headless -- --bench …: код 0, отпечаток того же боя
    # сравнить с Linux (пока предупреждение; с пакета баланса — провал)
  bench:        # пуш с «[bench]» в сообщении коммита (или dispatch с battles > 0,
                # если он заработает — см. ниже); основной стенд — в сеансе (8.6)
    # 4 процесса по 25, по сочетаниям и ролям, --swap; summarize.py → артефакт
  release:      # пуш, в котором godot/RELEASE получил новый номер (основная дверь);
                # плюс метка capella-v* и dispatch с release — если они работают
    # два zip и текст «как запустить» по-русски → GitHub Release
    # (gh release create $NUM … --target $GITHUB_SHA; permissions: contents: write)
```

- По документации GitHub фильтр `paths` к меткам не применяется — метка
  запускает сборку всегда. Проверить это первым же выпуском.
- **`workflow_dispatch` срабатывает, только если файл workflow лежит
  в ветке по умолчанию** — так в документации GitHub («This event will
  only trigger a workflow run if the workflow file exists on the default
  branch»; пробами не проверялось). Ветка по умолчанию — `master`
  с сайтом CineFlow, её мы не трогаем. Значит кнопка `release`
  и задание `bench` по кнопке, скорее всего, не заработают, пока
  workflow живёт только в `claude/capella-godot`.
- **Сайт CineFlow не задет**: фильтр `paths` + ветки Godot; Pages
  по-прежнему отдаёт master.
- **Игроку — страница GitHub Releases**
  (`https://github.com/afalin8-ui/cineflow/releases`): «для Windows»
  и «для Linux» (zip; для Linux можно приложить tar.xz), текст изменений
  и «как запустить» по-русски. Предупреждение заранее: Windows покажет
  SmartScreen у неподписанной программы — «Подробнее → Выполнить
  в любом случае». Репозиторий публичный, значит и выпуски публичны.
- **Как выпускать из сеанса.** Дверей три:
  1. метка `capella-v*` пушем — не проверено (удаление ветки пушем
     прокси отверг кодом 403, с меткой может быть так же);
  2. запуск workflow кнопкой с полем `release` (`actions_run_trigger`) —
     упирается в ветку по умолчанию (выше);
  3. **выпуск самим workflow по пушу в ветку**: задание `release`
     срабатывает, когда в `godot/RELEASE` новый номер, и создаёт метку
     и выпуск с `GITHUB_TOKEN` (`gh release create capella-v0.N … --target
     $GITHUB_SHA`, `permissions: contents: write`). **Проверено
     наполовину**: прогон C `38059353740` по пушу в ветку пробы создал
     ЧЕРНОВИК выпуска и залил оба zip (33,7 и 43,2 МБ); упал только
     следующий шаг — удаление с `--cleanup-tag` у черновика без метки
     (ловушка ниже). Выпуск с меткой — тот же вызов без `--draft`, но
     отдельно не проверялся: проверить в первой сессии G0. Метка,
     созданная `GITHUB_TOKEN`, по документации GitHub новых прогонов
     не запускает — двойной сборки не будет.
  Основная — третья. Первые две проверяются в первом пакете и
  записываются в `godot/CLAUDE.md`, но выпуск на них не держится.
- **Обратная связь — текстом.** Пользователь не разработчик: файл
  в `user://` (`%APPDATA%\Godot\app_userdata\…`) он не найдёт. Замер
  кадров, отчёт боя и запись для повтора игра отдаёт коротким текстом
  на экране и в буфер обмена (`DisplayServer.clipboard_set`) — его
  вставляют в чат; полный файл — рядом с программой и по кнопке
  «Открыть папку» (`OS.shell_open`). На Linux в тексте выпуска — что
  делать, если архиватор не сохранил право запуска (`chmod +x`).
- **Веб-сборки нет.** Она работает (A и C проверили в Chromium: wasm
  39,5 МБ, 10 МБ сжатым; тот же отпечаток боя), но в вебе только
  Compatibility — другая картинка; а GitHub Pages репозитория отдаёт сайт
  CineFlow из master, и переключать его нельзя.
- **Ловушки CI** (найдены C на сервере): имя `godot` в корне репозитория
  занято папкой — программу класть под другим именем (`godot-bin`);
  папку для сборки создавать заранее («export path doesn't exist»);
  у черновика выпуска не писать `--cleanup-tag` (метки у черновика нет).
  Заготовка A с ключом `push-tags:` — неверный синтаксис: метки задаются
  в `on.push.tags`.
- **Временные ветки проб** `claude/capella-godot-probe-A` (c006008), `-B`
  (9caf570, только README) и `-C` (af267e2) остались на GitHub: удаление
  пушем отсюда даёт HTTP 403. Удалить руками: GitHub → Branches → корзина.
  Вреда нет: их workflow срабатывает только на пуш в них же.

### 10.2 Соглашения
1. **Двери односторонние** (раздел 1): `sim/` ничего не знает о `view/`,
   `ui/`, `input/`; те пишут в модель только командами. Тесты: грепом —
   в `sim/` нет `Node`, `Time`, `Engine`, `Input`, `randf`, `randi`,
   `get_tree`; «бой с видом и без вида при `--fixed-fps` даёт один
   отпечаток».
2. **Типизация везде**; предупреждения `untyped_declaration` и `unsafe_*` —
   ошибки в настройках проекта. В модели — классы, не словари. Пробы
   с этими настройками НЕ собирались (не проверено): загрузчику JSON
   в `defs.gd` словари неизбежны, и если «небезопасные» обращения к ним
   там не обойти явными `as` и типами, предупреждение глушится
   `@warning_ignore` только в нём, с причиной в комментарии.
3. **Имена кода — по-английски, комментарии и тексты — по-русски**, как
   в `game/js`. Строки интерфейса — в `ui/texts.gd`.
4. **Пометки над функциями**: `# space.js:NNNN имяJS · часть NN, раздел`,
   `# ОТЛИЧИЕ: … (почему)`, `# ДОКТРИНА 09, §…`. Номера находок (C…, P…,
   ловушки 0N-M, М1–М15) — в комментарии у правила.
5. Время модели — `battle.time` и `Battle.STEP`; случайность —
   `battle.rng` (картинка — `fx_rng`); расстояния логики — `battle_dist`;
   оружие — по роли; «вооружён» — `can_hurt()`; видимость — `Vision.sees`;
   свойства корабля — функциями.
6. **Кнопки HUD — `FOCUS_NONE`, раскладочные узлы — `IGNORE`**, клавиши —
   по `physical_keycode`, числа в текст — форматом.
7. **В git лежат `*.gd.uid`** (Godot 4.7 создаёт их сам), `.godot/`
   и `build/` — в `.gitignore`.
8. Оптимизация бывает двух видов: равносильная (тот же бой с тем же
   зерном — тот же отпечаток побитно, C показал, что это проверяется)
   и меняющая поведение (отдельно, с сотней боёв до и после).

5. Задел узлов: функции вместо полей, `damage(…, from_dir)`, тормоз от

8. Стенд: команды, процессы, `--set`, `--swap`, флажки отката; «сторону

## 12. Что опровергнуто при проверке (не повторять)
- «`Input.parse_input_event` без окна до интерфейса не доходит» (B) —
  неверно: доходит всеми тремя способами подачи; тест B с подачей через
  `Input` без окна — 21 из 21.
- «Ошибка разбора — код выхода 0 и вечный прогон» (B) — верно наполовину:
  сломанный главный `-s`-скрипт или его `preload` — код 1; `--check-only` —
  1 на ошибке; вечно висит СЦЕНА со сломанным скриптом; код 0 — когда
  сломанный скрипт подгружен через `load()`. Практический вывод (timeout,
  `RESULT`, поиск `SCRIPT ERROR`) верен.
- «Ошибка скрипта роняет выпускную сборку» как общее правило — только
  вызов РОДНОГО метода у `null` (139). Скриптовый метод у `null` (G0a)
  и чтение поля у `null` НЕ падают, а молча ничего не делают.
- «Модель A вдвое быстрее B» — нет: 0,67–0,80 мс у A — среднее за весь
  бой; при пиковой нагрузке обе около 1,5 мс в редакторе.
- «До первого кадра размер окна 64×64» (A) — неточно: в `_initialize`
  он 100×100, после присваивания показывает заданный, а после первого
  кадра сам откатывается к 64×64. Вывод тот же: задавать после первого
  кадра.
- «`workflow_dispatch` срабатывает, только если файл workflow лежит в ветке
  по умолчанию» (документация GitHub, 9.2) — у нас неверно: вызов
  `actions_run_trigger` с `ref: claude/capella-godot` поставил прогон
  `38064945933`, файла в `master` нет (G0a). Пуш метки из сеанса —
  наоборот, не работает: HTTP 403.
- «Шаг 3,3–4,9 мс можно снять равносильными правками» (C) — не доказано:
  равносильная правка дала около 10% всего шага; буквальный перенос
  с доктриной — 4,56 мс и худший шаг 24 мс.
